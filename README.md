## Getting Started

The SDK supports Python 3.10 or later. Use the asynchronous generated methods
inside async code, or the `_sync` methods in synchronous code:

```python
from reacon_sdk import ApiClient, Configuration
from reacon_sdk.api.domains_api import DomainsApi

async def read_counts(api_key: str):
    configuration = Configuration(
        api_key={"ApiKey": api_key},
        request_timeout=30.0,
    )
    async with ApiClient(configuration) as client:
        return await DomainsApi(client).get_domain_counts(
            domain="example.com", _request_timeout=5.0,
        )

def read_counts_sync(api_key: str):
    configuration = Configuration(api_key={"ApiKey": api_key})
    with ApiClient(configuration) as client:
        return DomainsApi(client).get_domain_counts_sync(
            domain="example.com", _request_timeout=5.0,
        )
```

Every generated JSON/CSV request has a 30-second default total network deadline,
including pool acquisition, connection establishment, writes, and all body
reads. `Configuration.request_timeout` changes the client default. A numeric
`_request_timeout` overrides the total for one request. All values are finite,
positive seconds. The legacy `(connect, read)` tuple sets those phase limits;
the configured client total still applies even if the peer continuously sends
small chunks. `AsyncReacon(..., request_timeout=30.0)` exposes the same default
for its generated JSON resources. Streaming has separate idle/total options.

Cancel an async request through its task's `cancel()` method. The SDK propagates
`asyncio.CancelledError` and closes the pending connection. KeyboardInterrupt
cancels the pending synchronous request. A client may be reused after either
cancellation or a deadline. Use a client consistently in async code or sync
code; do not share its pool across event loops. Calling a sync method from an
event loop raises an error; use its async counterpart instead.

Owned pools close through `async with`, `with`, `await client.close()`, or
`client.close_sync()`. An HTTPX client supplied as `ApiClient(...,
http_client=your_client)` stays caller-owned. The SDK forces
`follow_redirects=False` per request even if the supplied client enables it.
Custom HTTPX transports or hooks must not add their own automatic retries.

Requests default to one attempt. Set `Configuration(safe_retries={"max_retries": 2})`
or `AsyncReacon(..., safe_retries={"max_retries": 2})` to opt into retries for
identity, domain counts and lead listing only. Override one request with
`_retry={"max_retries": 1}` or disable retries with `_retry=False`. Explicit
retries on unaudited operations fail before transmission. The legacy
`Configuration.retries` still accepts only `None` or `0`.

At most three extra attempts are permitted, for HTTP 429/502/503/504 only.
Transport, decoding and interrupted-body failures never retry. Backoff has
jitter, doubles from `base_delay` (default 0.1 seconds) and is bounded by
`max_delay` (default 2 seconds, maximum 60). `Retry-After` seconds or HTTP dates
set a minimum wait. If it exceeds the delay cap or remaining total deadline,
the last HTTP error is returned. Cancellation interrupts backoff. The original
total deadline covers all attempts, waits and response body reads.

### Bounded cursor iteration

`LeadsClient(client)` and `EmailsClient(client)` extend the generated resource
classes. `AsyncReacon.leads` and `.emails` expose them directly. Use `pages()` /
`items()` with `async for`, or `pages_sync()` / `items_sync()` with `for`.
Email mentions use `mention_pages()` / `mention_items()` and their `_sync`
variants. One-page methods remain available.

```python
from reacon_sdk import ApiClient, Configuration, LeadsClient

def first_contacts(api_key: str, team_id: str):
    with ApiClient(Configuration(api_key={"ApiKey": api_key})) as client:
        return list(LeadsClient(client).items_sync(
            team_id=team_id, limit=50, max_items=100, max_pages=5,
        ))
```

Iteration is lazy and never prefetches. Defaults are 100 pages and 10,000 items;
zero bounds make no requests. Requests cap their page size to the remaining
item bound. Filters and header-cursor precedence are preserved; empty pages
with a cursor continue and repeated cursors raise `ReaconPaginationError`.
Offset mixing is rejected. Every page disables retries so request bounds hold.
Use `_request_timeout` for a per-page deadline and native async cancellation.

Email pagination can charge for every page: set `only_if_free="true"` or
explicitly acknowledge `allow_paid_requests=True`. These bounds are not a
monetary spending cap. Early exit holds no open response; owned pools still
need their normal client context/close. Streaming never retries or reconnects.

Errors are inspectable without losing the original response:

- `ApiException` and its HTTP status subclasses expose `status`, `headers`,
  `request_id`, flat/nested API `code`, the original text `body`, `parsed_body`
  (JSON when valid), and the buffered HTTPX `response`. Undocumented, non-JSON
  and malformed error bodies remain available. Credit details stay in the body
  and headers; `Retry-After` is available without triggering a retry.
- `ReaconRequestTimeoutError` exposes `timeout_seconds` and `phase` (`total`,
  `connect`, `read`, `write`, or `pool`).
- `ReaconTransportError` retains the underlying connection error as `cause`.
- `ReaconResponseDecodeError` retains status, headers, request ID, text and raw
  body bytes when a successful response cannot be decoded as declared.

The generated `without_preload_content` variants return a buffered HTTPX
response; they finish its body within the same total deadline. Use the explicit
streaming helpers for streaming responses.

## Author





The service URL is fixed to https://api.reacon.io. SDKs do not accept a service URL override.

## Retrying requests

A timeout or dropped connection does not prove that the server rejected a request. Before retrying a write or credit-consuming operation, check its outcome. Only retry when the operation is safe to repeat; when present, respect the Retry-After response header. Keep application-level retries bounded as well: wrapping an SDK call in an unbounded retry loop can multiply requests and repeat side effects.

## Reporting failures

When reporting a failure, include the SDK package version and HTTP status. Include a request identifier if the response supplies one. Remove API keys and customer data from logs and bug reports. Redact Authorization and X-API-Key headers before sharing a request. Never include the API key in a URL or a screenshot.
